## 2026-09-29

### 🆕 端侧 MLFQ 调度：服务端五因子搬到网关的会话分配（开关默认 fcfs）

**背景**：`algorithm/mlfq/` 是服务端的**上层调度器**——客户端自己决定先派发哪个会话的
哪一轮，靠 trace 的未来信息算 cp/cr/tl。要验证它搬到端侧有没有收益，落点是**网关的
会话分配**：会话空出来时，是"谁先被条件变量叫醒谁拿"（FCFS），还是"给排队者打分、
只让最高分先拿"。

**新增**：

- `gateway/mlfq_sched.py`：纯逻辑内核，因子归一化与加权**照抄** `factors.py` 的口径。
  五个因子全部换成端侧**可观测近似**：cp = 本轮估算算力（估算 prompt token + max_tokens）、
  sa = 排队时长、pf = 本轮 prompt 与候选会话 `known` 前缀的重合比例、cr = 0（不可观测）、
  tl = 1/(1+距上次提问结束的空闲秒数)；另加 MLFQ 的**长任务分流**（估算 prompt 超阈值
  限流，默认 8192 tok、并发上限 max(1, NSESSION//2)）。
- 网关：`--sched-policy fcfs|mlfq`（`start_gateway.sh` 用 `SCHED_POLICY` 透传）、
  `--sched-weights`（默认沿用服务端 `0.4,0.3,0.15,0.1,0.05`）、`--sched-long-tokens`、
  `--sched-long-max`。`SessionPool` 只在"会话空出来 + 队列里不止一人"时走打分选人，
  **不抢占、不动 KV 记账**；`fcfs`（默认）路径与改造前**逐字节一致**。
- `bench_agent.py --hetero`：异构负载（各会话的 prompt/输出/工具等待按倍数不同）。
  ⚠️ 同构负载下五个因子没有区分度、排序退化为 FCFS，A/B 会看不出差别——这条写进了
  `PERF.md`。
- `PERF.md`：指标口径与 A/B 标准步骤；策略实现见 `gateway/mlfq_sched.py`。

**验证**：`mlfq_sched.selftest` 13 项纯算术全过（FCFS / sa / cp / pf / 长任务限流 /
权重解析）；桩网关带竞争（6 会话打 4 会话）分别跑通 `mlfq` 与 `fcfs` 两条路径、
无异常、KV 命中正常。

**板上 A/B 实测**（CM3588-Plus，32768 导出、`NSESSION=2`；4 个会话抢 2 个会话制造排队，
`bench_agent --hetero`（各会话规模 ×2.0/×0.5/×1.5/×0.75）；每种策略连跑 3 轮取中位数）：

| 指标 | fcfs | mlfq | 变化 |
|---|---|---|---|
| makespan | 94.88 s | **88.67 s** | **−6.5%** |
| 总输出吞吐 | 11.50 tok/s | **12.30 tok/s** | **+7.0%** |
| 气泡比 | 0.3776 | **0.3118** | **−17.4%** |
| E2E p50 | 14795 ms | 17928 ms | +21.2%（小任务变差） |

**解释**：端侧 cp 因子取"剩余算力大者"，等价于经典 **LPT（最长作业优先）**：把大任务
先塞进两条流水线，装得更满 → makespan 更短、气泡更少、总吞吐更高；代价是**短任务的
排队与端到端时延变差**（长任务先跑）。行为层面也确认了打分真的生效：第 1 轮里
`fcfs` 先服务小的 sess3（scale 0.75）、`mlfq` 先服务大的 sess2（scale 1.5），
两者在队列里的先后被**反转**。prefill/KV 命中两策略完全相同（0.556）——调度只改
"派给谁"，不改计算量。

注：这是单机 3 轮的中位数，收益量级（5%~7%）不大但方向稳定；真实 Claude 的流量
（主对话长 + 后台 Haiku 短）同样是异构负载，cp 因子会优先保证主对话。以真 Claude 的
端到端体验为准。

### 🆕 性能统计：`/v1/perf` + 每轮 `perf` 明细 + `bench_agent.py`（调度算法 A/B 的尺子）

**为什么**：要把 `algorithm/mlfq/`（服务端 MLFQ 上层调度）移植到端侧验证收益，先得有
可重复、可对比的测量口径——否则"快了"只是感觉。

**网关（`rkllm_gateway.py`）**：
- `_Request` 记三个单调时刻（`t_submit` / `t_first_token` / `t_done`），由此得到
  **TTFT**（REQ 写出→首段非空文本，不含排队）与 **E2E**；
- 复用 DONE 帧已有的 `prefill_tokens/prefill_ms/decode_tokens/decode_ms` 得到
  **prefill/decode 速率**与 **TPOT**，连同排队（`X-KV-Reuse.wait`）、KV 命中、
  会话号一起组成每请求记录；
- 新增 `PerfCollector`（进程内滚动窗口，最近 10000 条）与两个纯观测端点：
  `GET /v1/perf`（聚合分位数/吞吐/气泡比，`?full=1` 带明细）、`POST /v1/perf/reset`；
- 流式最后一个 usage chunk 与非流式响应体里各多一个非标准 `"perf": {...}` 扩展，
  并打一行 `[perf] {json}` 日志（`--verbose` 时），离线可 `grep` 分析。

**口径上的一个坑（已按"先记账再发 DONE"修）**：最初在 `[DONE]` 之后才把记录放进窗口，
客户端一看到流结束就查 `/v1/perf` 会读到少一条的聚合——越短的请求越容易踩到。现在
**先记账、后发 `[DONE]`**，`reset → 打负载 → 读一次` 才是准确的。

**基准（新增 `tools/bench_agent.py`，纯标准库）**：与 Claude Code 同构的负载——多会话

的 `METRICS` 对齐），`--compare` 直接给两次运行的"更好/更差"。

**验证**：`selftest_perf` 用确定性输入钉死分位数/吞吐/KV 命中/气泡比（`--selftest` 会跑）；

### 🐞 `start_gateway.sh` 收相对路径时，容量闸过得了、`MODEL_DIR` 却报 no such dir

**症状**：`cd serve && INSTALL_DIR=../install/rknn_multicard_demo MODEL_DIR=../../xyf_workspace/.../Qwen3.5-27B ./start_gateway.sh`
先打出容量闸的「上下文 = 32768 …」，紧接着却 `no such model dir: ../../xyf_workspace/...`。

**根因**：脚本先 `cd "$INSTALL_DIR"`，**之后**才 `[ -d "$MODEL_DIR" ]`。相对路径的参照系
从调用目录（`gateway/`）换成了安装目录，同一个字符串被解析到两个不同的地方——容量闸那一行
在 `cd` 之前跑，所以找得到模型，检查反而找不到。

**修法**：`INSTALL_DIR` / `MODEL_DIR` / `LOG` 在 `cd` 之前统一转成绝对路径（`_abspath`），
之后从哪个目录调用都成立。`B`（默认 `./rknn_multicard_demo.serve`）保持相对，它是**相对
安装目录**的产物名，不能跟着转。

### 🐞 网页「暂停」后点「继续」没反应：按钮只绑了 pauseTurn

**症状**（用户报的）：生成中点「暂停」能停；停下来之后按钮文字变成「继续」，但**点它没反应**，
只有在输入框里手动打「继续」发出去，才会接着往下写。

**根因**：`demo_4chat.html` 的按钮点击处理写死走 `pauseTurn(p)`，而 `pauseTurn` 第一行是
`if (!p.streaming || !p.requestId) return;`——暂停后 `streaming` 已经是 false，点击被这一行
直接挡掉。页面里其实早就写好了走 `continue:true` 的 `continueAnswer(p)`，**从未被调用**过。
（网关与后端的 STOP → RESUME 链路本身没问题，`selftest_continue` 一直覆盖着。）

**修法**：新增 `togglePause(p)` 按状态分发——生成中 → `pauseTurn`，已暂停 → `continueAnswer`；
按钮绑它。**测试也补了**：`page_check.js` 的暂停/继续那一节原来只验按钮文字与显隐（所以这个
bug 能全绿通过），现在直接点真的 click 处理器、用桩 fetch 记录打到哪个端点——生成中必须打
`/v1/stop`（带本轮的 rid）、暂停后必须打 `/v1/chat/completions` 且带 `continue:true`。
对旧页面跑会红（`FAIL: 暂停后点击「继续」没走 continue 请求`），修完全绿。

### 🐞 「继续」到一半再暂停，按钮消失、回答接不回去

**症状**（用户报的，紧随上一条）：暂停 → 继续 → 再暂停，**暂停/继续按钮直接不见**，
半截回答再也接不回去（只能重新问一句）。

**根因**：`continueAnswer()` 的 `finally` 无条件 `p.paused = false`。用户在「继续」的流里
又按暂停时，后端按约定停手、那一轮以 `finish_reason=abort` 收尾；但 `send()` 里那条
「abort → paused=true」的处置没有搬到 `continueAnswer`，于是 `finally` 把 paused 清成 false，
而按钮的显隐是 `p.streaming || p.paused` —— 两端都 false，按钮就没了。

**修法**：与 `send()` 对齐——`continueAnswer()` 成功路径里 `if (r.finish === "abort") p.paused = true;`
（统计行同时标「已暂停」）；`finally` 不再动 `paused`；请求失败时也把按钮留在「继续」上
（半截还在，可重试）。`page_check.js` 再加一条：喂一段以 `abort` 结尾的真 SSE 进
`continueAnswer`，断言跑完后 `paused=true`、按钮还在且写「继续」（对旧页面同样会红）。

### 🆕 3588 七个热区全画出来；1828 四张卡的结温也上页面了（板上加一个只读采集服务）

**第 2 条那个旧结论是错的，这里更正**：SDK 的 `RKNN3_QUERY_*` 里确实没有温度项，

**取卡温踩到的三个坑**：
- `rknn-smi` **要 root**（`/dev/pcie-rkep-*` 是 `crw------- root root`）。非 root 跑**不是报错**，
  是静默 `rc=255` 且**一个字都不输出**；按"解析不到就跳过"的写法，看起来就跟"这块板没有温度"
  一样。
- **同一时刻只能有一个 `rknn-smi`**：板上留着一个 `rknn-smi info -w`（守护式）的话，
  之后每次调用都 `Failed to initialize rknnsmi`。
- `-t temp` 的输出里**两行都含 `Temperature (C)`**：`Device Temperature (C)` 在这块板上恒为
  `NA`，`Chip Temperature (C)` 才是真值——按后缀匹配会让 `NA` 覆盖掉真值。

**为什么是"root 小进程写文件"而不是"给网关一条免密 sudo"**：网关是局域网上**无鉴权**的
常驻服务（下一条），让它具备拉起 root 进程的能力不划算。所以拆成两侧：
`rknn_smi_temp.py`（新增）以 root 每 5 秒跑一次 `rknn-smi info -t temp`，原子写
`/run/rknn-temp.json`；网关仍然是 pi，**只读**那个文件，读不到就画 `—`。这一半只读设备、
只写 /run 下一个文件，不监听、不联网。
⚠️ 写文件必须 `mkstemp` + `chmod 0644` + `os.replace`：**`mkstemp` 建出来是 0600，而读它的
是 pi 不是 root**，忘了 chmod 就是"文件在、读不了"，症状和"服务没跑"一模一样。

**采样失败不覆盖旧值**：脚本采不到时**不写文件**，于是 `ts` 不动、屏幕上的年龄继续涨——
"上次成功是 30 秒前"是看得出来的。要是照写一份空值，就成了"采集服务在跑、只是温度没了"。

### 🆕 演示页资源条：RK1828 每卡内存/NPU 忙时占比 + RK3588 内存/CPU/温度

**为什么**：板上跑着演示，屏幕上只有 tok/s。四张卡谁在干活、还剩多少余量、是不是快撑爆了，
全靠敲 `rknn-smi`——**而后端驻留时 `rknn-smi` 是取不到数的**（`Failed to initialize rknnsmi`：
设备同一时刻只认一个持有者）。所以这些数只能由**持有设备的那个进程**采，经帧协议报出来。

**三类数据的来路完全不同，别混**：

| 要看的 | 来路 | 边界 |
|---|---|---|
| RK3588 内存 / CPU / 负载 / 运行时长 | 网关自己读 `/proc/stat`、`/proc/meminfo`、`/proc/loadavg`、`/proc/uptime` | 与后端无关，后端死了这些照样有 |
| RK3588 温度 | 网关读 `/sys/class/thermal/thermal_zone*`，取最热的 3 个 | **只有 RK3588 的 7 个热区**（含它自己的 `npu-thermal`） |
| **RK1828 每卡内存** | `RKNN3_QUERY_DEVICE_MEM_INFO`，**后端**在推理之后顺手采 | 只有持设备者能查；查不到就保留旧值且**不更新采样时刻** |
| **RK1828 每卡"忙时占比"** | 后端累计每卡 `session_run` 的耗时 ÷ 墙钟 | **SDK 没有 NPU 利用率查询接口**，这是**算出来的** |
| 卡温 | —— | 卡是 PCIe 设备（`rkep`），**没有 hwmon、没有 thermal_zone**，拿不到 |

**改法**：

1. **后端新增 `STAT` 帧**（`main.cc`）：stdin 上一行 `STAT`（无载荷、无 rid）→
   `STAT <len>` + `<len 字节 JSON>`。载荷用 JSON 是因为这一帧是**嵌套**的（每卡一组数），
   排空格就得先定死字段序、以后加字段两边一起改。
2. **就地答复、不进调度队列**：排队的话它会被前面那条正在跑的长 decode 挡在后面——而
   "板卡正忙、想看看它在忙什么"恰恰是最需要它的时候。它只读原子量，零设备访问、零锁等待。
3. **快照在推理之后顺手采**（`record_stage_run_stat`）：`rknn3_query` 与 `rknn3_session_run`
   走同一条到设备的传输通道，SDK 没承诺并发安全 ⇒ 必须在这个卡的 `run_mutex` 里采，
   节流 2s（否则每轮 decode 多一次设备查询，实打实吃吞吐）。
4. **网关新增 `GET /v1/system`**：`{ts, host{...}, npu{busy_pct}, backend{alive,sessions,ctx_size,stats_age_s}, gateway{busy,bound,dead,waiting,uptime_s}}`。
5. **页面资源条**（`demo_4chat.html`）：CPU/内存/温度/负载 + 每卡 `NPU 忙时占比 / 内存 / 最紧 node 余量`，
   2s 轮询、页面切走就停。

⚠️ **加一种帧 = 后端与网关必须成对换**。这是同一个机制第二次咬人：网关的读线程对
**未知 tag 不消费载荷**，整条流会错位（第一次是 ERR 帧，见 2026-09-16 那条）。旧网关读到
`STAT` 帧会把 JSON 当下一帧的头行读 ⇒ 全 503。

⚠️ **`session_run` 有两个调用点，观测必须都记**：`run_stage_worker`（各段）与
`run_pipeline_once` 里**就地跑的 stage0**。第一版只记了前者，结果是**第 0 张卡永远报
`run_calls:0` / "还没采到内存"**——页面上三张卡在动、一张空着，看着像那张卡坏了。
主机测试 t12 抓到的（桩不喂 batch，夹具里只有 stage0 那一半会执行）。现在两处共用
`record_stage_run_stat`，漏抄不成立，但"worker 里那次调用还在不在"仍只有读代码和板卡能证。

**口径**（每条都写进了页面的说明文字，不是只写在这里）：

- **忙时用单调钟、不用 `gettimeofday`**：利用率是两次采样的差值之比，中间被 NTP 校一次表，

- **缺值画 `—`，绝不画 `0%`**：`0%` 是在说"这张卡闲着"，而 `—` 才是在说"不知道"。
- 第一次采样算不出 CPU%/忙时占比（没有前一个点），这时也是 `—`。

### ⚠️ 32K 导出 + 默认 `NSESSION=4` 会把四张卡压死（**要重启板卡**），真正的上限是每卡 2 路

**症状**：板上换上 32768 那份导出后，`CTX=32768 ./start_gateway.sh`（`NSESSION` 用默认的 4）
起不来。日志停在

```
[stage0] init stage: ... Weight sync chunk size resolved to 2097152 bytes
wait_event(0x100000): timed out        ← 卡在这里
recv MsgSessionInitAck fail!
```

**从没打出 `context init done`**。之后设备就僵了：任何加载都在 `rknn3_init` 上 `ERROR_PIPE`
（`errno=11`，`recv(MsgInitAck) fail, -9`），`systemctl restart rknn3` **也救不回来**
（四个 `rknn3_transfer_proxy` 全被带走 → 四张卡 `ddr load addr request failed` /
`Device request state: 0xffa70000`，退出码 234）⇒ **只能重启板卡**。

**根因不是 ctx，是路数**（早先记成"CTX=32768 加载失败"，错了）：
`CTX=32768 --sessions 1` 加载并推理成功（四个 stage `max_ctx_len=32768`，喂 9854 token 的
prompt 也跑通 ⇒ 32K 是真的）；变量只有 `--sessions`。KV 在 `session_init` 时按**每路满上下文**
一次性预分配，所以账是"上下文 × 路数"：

| | 每路 KV | 每卡总量 | 结论 |
|---|---|---|---|
| 32768 导出 | **406.7 MB/卡**（50.8 MB/node） | 装得下 2 路 | 1 路 smi 84/88%，2 路 93/95%，**3 路差 ~38 MB ⇒ 装不下** |
| 4096/8192 旧导出 | ~101 MB/卡 | 装得下 5 路 | 这就是"板卡硬上限 5"的来源 |

**`--ctx-size` 在这份导出上救不了**：一份导出只有一档 KV（`attn[0] n_lens=1 lens: 32768`），
请求 8192 时 SDK 仍打 `chosen kvcache_buffer_lens: 32768`。

**改法（三层，缺一层就还会再撞）**：

1. **`start_gateway.sh` 加容量闸**（🆕）：从 rope 外置张量的大小反推上下文
   （每个位置 256 字节 + 432 字节头 ⇒ 8192→2.0 MiB、32768→8.0 MiB），按
   `可用 KV ÷ 每路 KV` 算出上限并与 `NSESSION` 比，超了**直接拒绝启动**并说明后果；
   要硬上得显式 `FORCE_SESSIONS=1`。这条线性式同时对上三个实测点（4096→5、8192→5、32768→2）。
2. **网关把 `--ctx-size` 报出来**（🆕）：`/health` 多了 `ctx_size`，页面才可能知道自己
   待在一个多长的上下文里。
3. **页面不许自己编窗口数**（🆕，见下一条）：上限取 `/health` 的 `sessions`。

顺带纠正：`--ctx-size` **不是**能随意调小的旋钮——它是"请求"，会在模型编进去的那组候选里
被夹住（老 4096 导出请求 8192 拿到 4096；新 32768 导出请求 8192 拿到 32768）。权威答案是
SDK 日志的 `chosen kvcache_buffer_lens`。`RKNN3_QUERY_ALLOCATION_INFO` 在 RK1828 上**不更新**
（`SUM: kvcache` 建会话前后不变），只有 node free 那条数可信；`rknn-smi` 在后端驻留时取不到数。

### ⚠️ 演示页的"聚合 tok/s"口径改了：四路长度不齐时它会凭空变小

**症状**：一次真实四路（网页）屏幕上写着

```
4 路并发：合计 2095 tok / 墙钟 135.7s → 聚合 15.43 tok/s
9.83 / 10.07 / 11.80 / 9.72 tok/s ……（四个面板各自的速率）
```

四个面板**每路都是全速**（9.8~11.8，单路基线约 10.6），可顶上那个数看着跟单路是一个量级，
读出来就是"四路并发没什么用"。

**根因不是算错，是口径**：那 135.7s 里只有前 ~18 秒是四路在跑——**有一路 1602 token 跑了
135.7s，另外三路约 16s 就收工了**，剩下 120 秒**只有一路**在跑。`Σtok / 墙钟` 把"一路的
吞吐"摊进了"四路并发"的分母，于是：

- **各路速率和** `Σ(tok_i/el_i)` = **41.42 tok/s** ← 四路同时跑时整机的总产出
- **墙钟摊薄** `Σtok/墙钟` = **15.43 tok/s** ← 平均只有 **1.37/4** 路在跑的那个数
- 两者差 **2.7 倍**，不是误差，是**两个不同的问题**

**改法**（`demo_4chat.html` 的 `summarize()`）：

| | 口径 | 用在哪 |
|---|---|---|
| 各路速率和 | `Σ(tok_i/el_i)`，**与单路基线同口径** | 横幅**主数**；**伸缩比只用它**（41.36/10.63 = 3.89×，用摊薄值会算出 1.45×） |
| 墙钟摊薄 | `Σtok_i/墙钟` | 跟在后面，且**只在四路长度齐时才有意义** |

长度不齐时（`Σel/墙钟 < n-0.5`）横幅自己标出来：`四路长短不齐，平均只有 1.37/4 路在跑，
墙钟摊薄 15.44 tok/s（空转的路也算进了分母，别当并发性能看）`；排队警告移到整句**最后**
（它撤的就是刚印出来的伸缩比）。

**顺带修了一个检查的盲区**：`page_check.js` 以前是**自己** `panels.map(send)` 发四路，
页面里 `summarize + setSum` 那两句压根不执行 ⇒ **汇总行怎么算的没有任何检查覆盖**。
现在把「②」的处理器提成 `runAll()`，检查直接调它（`lastRound()` 取回结果），
并核对页面上真写出来的那句。三个变异体（伸缩比改用摊薄值 / 稀释警告永不触发 /
把摊薄当主数印）都被抓住。

### 🐞 NPU 空着，用户却在干等：第 N+1 段对话得等到某一段静默满 `IDLE_TTL`

**症状**：网页某一格 `158 tok · 100.9s · 1.57 tok/s`，而那一刻 **NPU 上一个请求都没在跑**。

**根因**：会话池只有一条回收阈值 `IDLE_TTL`（300s），且 `_reap_idle_locked` **只在 `acquire`
里被调用**。于是 N 段对话把 N 个会话**绑着不用**时，第 N+1 段对话要一直等到某一段**静默满 300s**
才拿得到会话——这中间 NPU 全空。板上实测（`page_repro.py`，四段对话静默 70–90s）：第 5 段
**排队 226.0s**，而它拿到会话的时刻正是 `web-1` 跨过 300s 的那一刻。`1.57 tok/s` 是**端到端**的
数——页面把这段排队也算进分母了，屏幕上分不出"模型慢"和"根本没轮到它"。

**修法**（两层，第二层只在第一层不够用时降下来）：

| 层 | 阈值 | 什么时候用 | 收几段 |
|---|---|---|---|
| 一（原有） | `IDLE_TTL` 300s | 只要有人问就一直在跑 | 所有静默超阈值的 |
| 二（新，`--contend-idle`） | 15s | **只有**一个空闲会话都找不到、这一轮非等不可 | **只收最闲的那一段** |

`idle_ttl=0` 仍是**总开关**：第二层绕过它就等于把"0 = 不回收"这条契约作废，而回归套件正是靠
它来证明自己真的在主动 `close`（不是碰巧被回收救了）。

**顺带把"等"变成可见的**：`X-KV-Reuse` 加 `wait=`、日志 `lease:` 行排过队就打 `排队 X.Xs`、
`/v1/pool` 报 `contend_idle_s`、页面排过队时行内显示 `⏳ 等待空闲会话…`、统计行拆成
`（其中排队 X.Xs，实际推理 Y.Ys）`、四格汇总栏加"有 N 路排过队 → 伸缩比不可引用"。
**不这么做就没法自证**：排队在 tok/s 上只表现为"变慢"，看不出异常，而那个 tok/s 恰恰是被排队污染的。

**板上实测（2026-09-18）**：

| | 四段对话静默 | 第 5 段对话 |
|---|---|---|
| 改前 | 70–90s | **排队 226.0s**（等满 `IDLE_TTL`） |
| 改后（在静默 0.5s 时敲） | 0.5s | 进队列，**15.4s** 拿到会话（`wait=15.0`） |
| 改后（在静默 24–42s 时敲） | >15s | **没进队列**，`wait=0.0`、TTFT 1.17s |

`reaped_total` 精确地 0→1→2（一次只收一段）；静默 41.8s 的两段**不被收**——只在真有人敲门时才动。
日志长这样：`[pool] 会话回收：id:web-3 静默（有人排队） 73.0s > 15.0s，s3 交还给排队者`、
`[gateway] lease: session=0 reset=True sent=204/204 bytes (base=0) 排队 15.0s`。
⚠️ 改的是**网关进程**，必须重启（模型重载 ~240s）；旧件留 `gateway/bak_20260918_contend/`。`b5483bd`
